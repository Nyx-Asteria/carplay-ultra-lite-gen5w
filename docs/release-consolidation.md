# Release consolidation policy

Required before every RC, not just RC11. Develop on a dedicated branch based on the previous verified release. Consolidate related implementation and fix commits since that baseline into coherent reviewable changes; retain upstream ancestry and meaningful milestones. Do not rewrite published tags or release history. Preserve a recoverable pre-consolidation snapshot and compare Git trees, documenting intentional cleanup separately from history-only changes. Review obsolete experiments, settings, documentation, dependency pins, generated recipes and diagnostics; preserve relevant evidence and attribution. Run full regression and signed package verification on the final consolidated commit. Pin companion revisions and verify coexistence before release. Publish automatically after successful coordinated release verification, as a non-draft prerelease with a comprehensive changelog and permanent author signing identity. Never reuse a verification result from a different source commit.

## Native build provenance and package gate

Development CI uploads the generated native recipe, its SHA-256, exact source commit and compiler/linker versions as a commit-specific artifact. A development artifact is not a signed package. The signed-bundle workflow rebuilds the recipe independently on the selected source commit, checks byte-for-byte equality against the recipe extracted from the signed CPUL ZIP, verifies all seven package signatures and records actual checkout SHAs, generated recipe digest, author UUID and toolchain in BUILD-PROVENANCE.txt. Bundle checksum verification includes the seven packages, changelog, testing documents and provenance. This records build inputs and verifies package content; it is not a cryptographic attestation of source reproducibility or vehicle behavior. Publication follows successful verified release builds under the owner-authorized release gate.

## Non-publishing candidate build

For RC11, the exact commit title `Release 1.0.0-rc.11` on `rc11-final` triggers signing and automatic publication after the package job succeeds. Other pushes run unsigned development regression only. Manual dispatch defaults to publish=false, with publish=true available for an intentional release run. Final WCP/STBT pins and expected manifest versions are locked; their CI passed. The package job independently runs matched-source regressions, regenerates the native recipe, checks signed package equality, signatures, and checksums. No second approval required.

## Synchronized versioning after RC11

RC11 completes the existing package numbering: CPUL 1.0.0-rc.11, WCP 2.2.1-rc.7, STBT 1.0.0-rc.4 (final companion revisions pinned). The next coordinated development release is 3.0.0-rc.1, not RC12. CPUL is the version authority for the project-controlled packages. A package with no relevant change may skip an RC rather than publish an unnecessary build; when it next releases, it adopts the current CPUL version exactly. For example, if STBT last released 3.0.0-rc.1 and skips RC2–4, its next release alongside CPUL RC5 is 3.0.0-rc.5. Preserve permanent package IDs and signing identities; never retag previous releases. Independent upstream dependency versions remain separately pinned. Update manifests, workflow expectations, release names, test guide paths and changelogs for the new series together, not during RC11. Release membership follows the coordinated CPUL version policy; successful gated release builds publish automatically.
