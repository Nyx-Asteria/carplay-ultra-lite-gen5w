# Release consolidation policy

Required before every RC, not just RC11. Develop on a dedicated branch based on the previous verified release. Consolidate related implementation and fix commits since that baseline into coherent reviewable changes; retain upstream ancestry and meaningful milestones. Do not rewrite published tags or release history. Preserve a recoverable pre-consolidation snapshot and compare Git trees, documenting intentional cleanup separately from history-only changes. Review obsolete experiments, settings, documentation, dependency pins, generated recipes and diagnostics; preserve relevant evidence and attribution. Run full regression and signed package verification on the final consolidated commit. Pin companion revisions and verify coexistence before release. Publish only with explicit owner approval, as a non-draft release with a comprehensive changelog and permanent author signing identity. Never reuse a verification result from a different source commit.

## Native build provenance and package gate

Development CI uploads the generated native recipe, its SHA-256, exact source commit and compiler/linker versions as a commit-specific artifact. A development artifact is not a signed package. The signed-bundle workflow rebuilds the recipe independently on the selected source commit, checks byte-for-byte equality against the recipe extracted from the signed CPUL ZIP, verifies all seven package signatures and records actual checkout SHAs, generated recipe digest, author UUID and toolchain in BUILD-PROVENANCE.txt. Bundle checksum verification includes the seven packages, changelog, testing documents and provenance. This records build inputs and verifies package content; it is not a cryptographic attestation of source reproducibility or vehicle behavior. No publication without explicit approval.
